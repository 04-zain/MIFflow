Source layout

The desktop and the command line use the same Python service to run an analysis. To trace a setting from a desktop form to a saved result, follow the form and its submitted request into the stage that performs the calculation. The processing guide explains where Python, Groovy and Java take part.

Desktop forms and processing requests

The launch commands are registered in pyproject.toml. mif-desktop starts the Qt application. mif-batch starts the batch command-line interface. Both use the batch service to open an analysis, retrieve a waiting review or continue processing after a decision.

To find a desktop control, start with the page in gui/qt. For a waiting review, follow the field name into the code that creates the form and interprets its submitted values. For example, the marker review widget draws the histogram and lets the researcher move the gate. The marker review presenter defines the choices and translates the selected cutoff into the response used by the batch service.

To find the inputs to a stage, start with the task in orchestration. During setup, analysis_setup.py and manifest_draft.py assemble the samples, image locations and method choices that define the run. The scheduler determines when a task can start. Its stage executor selects the accepted images, regions, measurements or models and passes them to the calculation. For a task that uses QuPath, the native runner launches the registered Groovy script with that request.

To trace a streaming review, follow the request through the remote client and the cluster review page format. The desktop opens the form in cluster_reviews.py. For an action inside that form, check where the cluster dialog sends the request and how it returns the result to the page. Annotation drafts, landmarks and figures have separate transfer routines under orchestration/cluster.

Reading and preparing images

Source inspection identifies the series, channels and physical calibration in an image file. Once the researcher selects a series, reviewed_source.py opens its pixels through the appropriate image reader. To trace an incorrect channel or image level, follow that selection into the request for a specific image region.

To follow a pixel through spectral unmixing, start with the regional processing engine. For each region, normalization.py applies the reviewed intensity corrections before the solver estimates the component intensities. The grouped, float32 and tensor solvers are in the same directory. To follow those intensities into an image on screen, inspect the image writers that store the OME-Zarr arrays, then the Java image reader that opens them in QuPath. Image layout and compression

Tissue, alignment and classification

Operation Where to follow the calculation
Detect and review tissue The tissue scripts create or apply the detector and return proposed tissue sections. Java geometry routines match sections and calculate their quality measures. The tissue detection module records the detector and reviewed sections.
Select analysis regions The QuPath scripts read the boundaries selected on the image. The analysis domain module identifies the areas that subsequent stages may use.
Align a paired image The registration module handles the fitting and transfer requests. Follow the registration scripts for Elastix and Transformix calls, RegistrationImageViews for the fields used in fitting, and the Java registration code for landmark transforms and geometry checks.
Train and apply a classifier Batch training organizes the references and subject allocation. The classifier scripts pass training data to the Java classification code, which prepares the features, fits the OpenCV model and calculates predictions and evaluation scores.
Use KRONOS features The encoder preparation selects the marker panel. The Java patch provider extracts features using the fixed encoder. For the tissue graph, follow the saved patch features into graph training and the fitted graph into GraphHeadKernel.

Cells, phenotypes and secondary structures

Segmentation. For InstanSeg, begin with the stage script and follow the tile detections into the Java segmentation code, which reconciles outlines where tiles overlap. Cellpose-SAM and StarDist enter through the alternative segmentation script. Cellpose runs in a Python worker and StarDist runs through its QuPath extension.

Cell measurements. The measurement plan identifies the columns to calculate. The measurement script supplies the image, cell outlines and selected measurements to Java. MeasurementRows calculates the per-cell values, including marker intensities and measurements derived from cell or nuclear geometry. PopulationMembership identifies the regions to which each cell belongs.

Cell phenotyping. Start in batch_phenotyping to see which cells and measurement columns enter a fit. Then follow the selected method.

  • For marker rules, thresholds.py fits the gates and marker_rules.py applies the ordered rules. For Nimbus, the image script supplies marker pixels and cell masks for scoring.
  • For supervised phenotyping, the reference script matches each labelled point to a cell. supervised.py uses those cell IDs to prepare the training data. For image-based features, the KRONOS cell script requests physically calibrated crops and masks from CellImageSamples.
  • For unsupervised phenotyping, clustering.py prepares the selected features. clustering_methods.py implements the PhenoGraph and FlowSOM fitting routes. Follow the fitted groups into cluster_review.py to trace a reviewed assignment.

Secondary structures. The Java region code calculates geometry and cell membership for the detected regions. roi_validation evaluates the selected criteria. The region review scripts collect the evidence and save the accepted regions and their membership.

Follow a saved result

For cell tables, cell_store.py writes batches of cells to Parquet and builds the index for looking up a cell by ID. To trace which table a later stage read, follow the saved dataset selection. It identifies the version the coordinator accepted after the writer completed the dataset.

To identify which result a stage used, start with batch_state.py. The saved state/head.json identifies the current plan and selected results. batch_history.py records changes to that state. batch_progress.py produces the state/current-progress.json summary shown on Run. Files in an analysis folder

To inspect the values in a cell result, follow the selected dataset into datasets/collection.py. It opens the cell outlines together with accepted edits and the requested measurement or phenotype columns. Cell IDs link those records within a segmentation result. A whole-population calculation can read the requested columns in batches. The Java cell reader uses the same IDs and field definitions when QuPath requests the outlines and labels in the displayed region. For an export, exports.py and spatial_handoff.py identify the datasets that the recipient can open. Reading selected cells and columns

Change a default, script or installed component

For the initial value on a new form, look in config/defaults, loaded by _defaults.py. To change which external release Software setup locates or installs, use config/software, _software.py and the setup routines. An existing analysis keeps the settings it has already saved. Analysis and software settings

For a QuPath script, edit the source under qupath/scripts. The script registry identifies the packaged entry points. Before running a project stage, we add the shared startup checks and save the prepared script and its checksum with the run. If you launch MIFflow from an installed package, reinstall after changing a script so the runner loads that change.

Changes to the Java classes or their service registrations require rebuilding the extension. For changes to the distribution itself, follow setup.py for the Python package and packaging for the portable editions. The build guide describes how to check the installed programs and resources.

For a worker startup or resource issue, follow the task allowance into the process controls and QuPath runtime. The launch settings limit memory, threads and caches.
